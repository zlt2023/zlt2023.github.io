流量漏斗模型与高并发架构：从零设计千万级秒杀系统

发表于 2026-04-02 分类于 后端开发

最近独立设计并开发了一套高并发秒杀系统。在这个项目中，系统不仅需要应对大流量冲击，还要保证绝对不发生“超卖”问题，同时要兼顾用户体验和系统可用性。今天就带大家从零开始，复盘这套秒杀系统的完整核心技术方案。

一、技术栈选型

俗话说“工欲善其事，必先利其器”，在动手前，首先敲定了全栈系统的技术栈栈：

  • 前端：Vue 3 + Vite + Element Plus + Pinia + Axios
  • 后端：Java 17 + Spring Boot 3 + MyBatis-Plus
  • 缓存：Redis 7 (Lua 脚本)
  • 数据库：MySQL 8
  • 消息队列：RabbitMQ
  • 安全认证：JWT (无状态Token)
  • 构建部署：Maven

整体架构采用了前后端分离模式，用户端与管理端也进行了独立拆分，保证了核心买家链路与后台管理链路相互隔离。

二、核心架构思想：流量漏斗模型

面对瞬时极大的并发流量，如果让所有请求都打到数据库，系统必然瞬间崩溃。秒杀架构的核心思想其实非常简单，就是四个字：层层拦截（即流量漏斗模型）。绝不让高并发流量直接打到 MySQL。

以下是我们的 6 层防御体系设计：

  1. 第1层：前端防护 (拦截大量重复点击)
    • 按钮防抖：用户点击抢购后，按钮立刻置灰 3 秒。
    • 精确拦截：倒计时未归零时按钮处于禁用状态。
  2. 第2层：Nginx 限流 (拦截恶意/超频请求)
    • 通过 limit_req 模块限制单 IP 每秒最大请求次数。
    • 配合 IP 黑名单过滤非法请求，拦截约 40% 的异常流量。
  3. 第3层：接口安全校验 (拦截脚本/Bot请求)
    • JWT 身份认证，保证真实用户才能下单。
    • 动态路径 Token 校验：秒杀地址不是固定的，而是先获取一个 60 秒过期的 pathToken，再带着它发请求，拦截 30% 脚本直刷请求。
  4. 第4层：JVM 内存标记 (最快失败，L1缓存)
    • 通过 localOverMap 在 JVM 本地缓存商品售罄状态。一旦售罄，直接在 JVM 层驳回请求，连 Redis 都不用去查。
  5. 第5层：Redis Lua 原子扣减 (核心准入校验)
    • 使用 Hash 存储活动信息，Set 判重。
    • 利用 Lua 脚本原子性地完成：状态校验、时间校验、库存预占、防止重复购买。一次网络往返搞定所有验证，将 99% 的无效请求拦截在 Redis 层。
  6. 第6层：RabbitMQ 异步入队 (保护数据库)
    • 只有 Redis 扣减成功（也就是那 1% 能买入预占名额的用户）的请求，才会被扔进消息队列。
    • 消费者以平稳的速度消费订单消息，实现“削峰填谷”，最终将数据落盘 MySQL。

三、Redis 如何抗住高并发与防超卖？

如何解决超卖问题是秒杀系统的灵魂。在我的方案中，强依赖 Redis Hash 数据结构和 Lua 脚本来实现绝对安全的原子扣减。

我们统一定义了缓存 Key 规范：

  • seckill:info:{id}：Hash 结构，存储核心元数据（价格、库存、开始/结束时间、上架状态）。
  • seckill:bought:{id}：Set 结构，存储已成功购买的用户 ID，防止一人多买。

(为了避免秒杀开始瞬间穿透，还设计了缓存预热机制，在 Spring Boot 启动或管理端手动重载时，提前将秒杀商品元数据写入 Redis Hash 并设置过期缓冲时长，防止内存被无效活动占满。)

四、RabbitMQ 异步下单与可靠性保障

用户在前端点击秒杀看到“排队中，请等待结果…”时，后端实际上正在通过 RabbitMQ 异步平稳地生成订单。

异步下单流程简述：

  1. Redis Lua 返回预占成功 (1) 后，发一条包含雪花算法 requestId 标识的消息至 seckill.exchange。
  2. 消费者监听到消息，通过获取 Redis 分布式锁 (setnx) 避免高并发下的极低概率重复消息执行。
  3. 数据库开启事务：执行扣减 MySQL 库存 (UPDATE ... SET available_stock = available_stock - 1 WHERE available_stock > 0)。这里利用乐观锁机制做数据库兜底防超卖。
  4. 插入 MySQL 订单数据 t_seckill_order，利用唯一的联合索引进行最终重买兜底。
  5. 更新 Redis 中的抢购结果为排队成功（这样前端轮询 /api/seckill/result 时就会看到抢购成功，并调转去支付），最后在 MQ 消费端进行手动 ACK 确认。

万一因为某些原因失败了怎么办？
如果兜底下单失败（比如 MySQL 并发冲突或宕机问题），程序捕获异常后必须回滚 Redis 预占：利用 INCR 恢复 Redis 库存，并用 SREM 移除该用户的购买记录标记，随后更新抢购状态为“抢购失败”。该过程亦包含 3 次失败重投策略，超过上限则交由死信队列（DLQ）进行人工监控并处理。

五、超时未支付如何释放库存？（延迟队列机制）

真正的线上秒杀还要面临一个真实痛点考验：恶意的羊毛党或者纠结的用户锁了库存但不去付款（占坑不拉屎）。

在消费者处理完创建订单并提交事务后，系统会向 RabbitMQ 下发一条带有 15 分钟 TTL 限制的延迟消息。

  1. 15分钟过后，消息过期并被转发至设置好的死信交换机 (DLX)，流入 cancel.queue。
  2. 超时消费者拉取消息，检索该订单状态。
  3. 如果此时订单仍是 待支付 (0)，执行原子更新取消：UPDATE status = 3 WHERE status = 0。
  4. 反向补偿链路：MySQL 增加库存归还 +1、Redis 恢复库存归还 +1、移除防重购买 Set 集合内标志，并且清除 JVM 的已售罄缓存标记（这就意味着之前卖光的商品，此时可能又重新亮起购买按钮允许后续排队者去抢空出的名额了）。

六、安全防护设计：不给羊毛党任何机会

单靠后端性能优化还不够，对各种脚本协议和恶意篡改必须重重防护：

  1. 接口动态隐藏（动态路径设计）
    这招杀伤力极大。如果前端的秒杀接口是 /api/seckill/buy?goodsId=1 这样固定的，那黄牛可以直接越过前端发送请求。我的方案中，必须先请求后台 GET /api/seckill/path/{id} 分配一个随机 pathToken (存入Redis, 60s有效期)。提交最终下单时 POST /api/seckill/{token}/execute，匹配不上或过期通通不认，从而完全隐藏了底层的核心接口。

  2. 限流切面的设计 (@RateLimit 注解)
    开发了自定义注解 + AOP 拦截体系 + Redis 计数器。业务只需要标记 @RateLimit(maxCount = 5, seconds = 5)，系统就会自动对请求 IP 和用户账号做限流，拦截极高频非人点击。

  3. 接口幂等与防并发竞态的严密校验
    更新和写操作坚决不用 SELECT .. 然后再 UPDATE .. ，完全利用 SQL 提供的原子防竞态能力 (TOCTOU)，在语句后加入状态判定和条件锁定操作。

七、极端场景数据一致性对账（补偿任务）

就算上了全套隔离，如果遇到服务器断电宕机怎么办？我在代码结构中专设了 task 包。
后台有一个 Scheduled Task 定时任务，扮演“包青天”对账角色：每 5 分钟遍历一次所有存活运行中的在线秒杀活动，比对 Redis Hash 中的剩余库存和 MySQL 中的 available_stock。只要两头对不上号，强制以 MySQL 落盘数据为准覆盖 Redis（记录详细对账告警日志）。这样即使缓存崩溃也能迅速自我恢复纠正。

写在最后

这套系统耗时两周完整落地，可以说是麻雀虽小五脏俱全。架构设计虽然经典，但只有亲自动手才体会到了其中坑连坑的奥妙：诸如 Lua 脚本和 Redis 数据结构结合的细节、RabbitMQ 分布式解耦导致的最终一致性要求、网络极度延迟情况的前端防抖轮训等等。

面对性能瓶颈分析问题、解决问题，才是做后端的最大乐趣。大家如果有建议或者疑问，欢迎在评论区探讨交流！
